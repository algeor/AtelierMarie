## ADDED Requirements

### Requirement: Product embeddings are persisted for reuse
The backend SHALL persist product embeddings with enough metadata to reuse them for recommendations and future semantic search.

#### Scenario: Embedding record identifies model
- **WHEN** a product embedding is stored
- **THEN** the record includes product ID, embedding model identifier, embedding vector, source text hash, and timestamps

#### Scenario: Embedding source uses product content and taxonomy
- **WHEN** the system builds embedding input text for a product
- **THEN** it includes available localized names, localized descriptions, product type, category, labels, and materials

#### Scenario: Product content change marks embedding stale
- **WHEN** product text or taxonomy fields used for embedding input change
- **THEN** the system can detect that the stored embedding is stale by comparing source text hash and model identifier

#### Scenario: Embedding refresh is repeatable
- **WHEN** the embedding refresh job runs multiple times for the same unchanged product and model
- **THEN** it updates or preserves one current embedding record rather than creating duplicates

### Requirement: Semantic similarity improves recommendations when available
The backend SHALL add embedding similarity to recommendation scoring only when compatible embeddings are available.

#### Scenario: Compatible embeddings contribute score
- **WHEN** selected and candidate products have embeddings from the same model
- **THEN** semantic similarity contributes to the candidate recommendation score

#### Scenario: Incompatible embedding models are not compared
- **WHEN** product embeddings were generated by different models
- **THEN** the service does not combine them in the same vector similarity comparison

#### Scenario: Missing embeddings do not break recommendations
- **WHEN** embedding data is missing for some or all candidate products
- **THEN** the recommendation API remains functional using rule-only scores for those candidates

#### Scenario: Embedding provider unavailable during refresh
- **WHEN** embedding generation fails during a refresh job
- **THEN** existing product listing, product detail, and rule-only recommendations remain functional

### Requirement: Semantic matching can support future search
The semantic matching layer SHALL be reusable for future query-to-product semantic search without replacing existing full-text search.

#### Scenario: Product-to-product matching reuses product embeddings
- **WHEN** recommendations are generated for a selected product
- **THEN** the service can use the selected product's stored embedding with compatible candidate embeddings

#### Scenario: Query-to-product matching can reuse product embeddings
- **WHEN** future semantic search embeds a user query
- **THEN** the service can compare that query embedding against the same stored product embeddings used by recommendations

#### Scenario: Existing full-text search remains available
- **WHEN** the existing product search service is called with a text query
- **THEN** current full-text search behavior remains available and is not replaced by semantic matching

#### Scenario: Semantic scoring can be combined with filters
- **WHEN** semantic matching is used with product filters such as product type, category, labels, or in-stock-only
- **THEN** the service applies those filters before returning public results

### Requirement: Semantic matching tests cover persistence and fallback
The backend SHALL include focused tests for embedding persistence, refresh detection, similarity scoring, and safe fallback behavior.

#### Scenario: Persistence test stores one current embedding
- **WHEN** a test refreshes an unchanged product embedding twice
- **THEN** it verifies only one current embedding record exists for that product and model

#### Scenario: Similarity test ranks closer product higher
- **WHEN** a test seeds compatible embeddings with different cosine similarity values
- **THEN** it verifies the more similar candidate receives the higher semantic contribution

#### Scenario: Fallback test handles missing embedding dependency
- **WHEN** embedding generation is unavailable in a test
- **THEN** it verifies recommendation behavior does not fail solely because embeddings cannot be generated
